## 1. 背景与目标

### 1.1 背景

现有邮件客户端（Outlook、Thunderbird、Foxmail、Spark）在信息密度、排版、交互节奏上无法满足个人审美与使用习惯。本项目不以"功能更全"为目标，而是**以重构一个自己满意的邮件阅读界面为核心**，用最小可用功能支撑 UI 迭代。

因此产品本质是：**一个可完全掌控界面的本地邮件阅读器**，而非通用邮件客户端。

### 1.2 产品目标

1. 提供一个可长期自用、界面完全自主设计的 Windows 桌面邮件阅读器。
2. 只做"收信 + 阅读 + 整理"，把复杂度压到最低，让 90% 的工程量投入 UI/交互。
3. 同步内核与 UI 彻底解耦：UI 只用假数据也能完整开发，替换 UI 不影响同步层。

### 1.3 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| 发送邮件（SMTP 发信、草稿、回复/转发） | 明确需求外；可后续以独立模块扩展 |
| 日历 / 联系人 / 任务 | 群件复杂度，与 UI 目标无关 |
| Exchange / EWS / Microsoft Graph / Gmail API | 只走 IMAP；降低协议与合规成本 |
| macOS / Linux / 移动端 | Windows 单平台，可用 Windows 专有能力（safeStorage、Toast） |
| 云同步、多设备、账号漫游 | 单机本地存储 |
| 插件系统、主题市场 | P2 之后再评估 |
| 商用、闭源、分发收费 | 开源非商用，GPL 兼容性不作为约束（但也尽量避免 GPL 依赖以便日后换协议） |

### 1.4 成功标准（可量化）

| 指标 | 目标值 |
| --- | --- |
| 冷启动到可交互 | < 1.5 s（SSD、i5 级以上） |
| 邮件列表滚动帧率 | 10,000 封下 ≥ 55 fps |
| 常驻内存 | < 350 MB（单账号、常驻托盘） |
| 样式改动反馈 | Vite HMR < 300 ms |
| 首次同步 2,000 封 | < 60 s（10 Mbps 以上） |
| 新增一个界面模块耗时 | < 30 min（模板化，shadcn 组件即取即用） |
| 阅读一封 5 MB HTML 邮件的渲染耗时 | < 300 ms |

## 2. 用户与场景

### 2.1 用户画像

单一用户：开发者本人。技术能力强，能自行配置 IMAP 参数、获取授权码、排查连接问题。**不需要**面向小白的引导式配置。

### 2.2 核心场景

| 编号 | 场景 | 频率 |
| --- | --- | --- |
| S1 | 开机后挂后台，收到新邮件时看到 Windows 通知 | 每日多次 |
| S2 | 打开应用，扫一眼未读列表，点开阅读 | 每日多次 |
| S3 | 切换多个邮箱账号（如 QQ + 自建域名）查看 | 每日 |
| S4 | 用关键词搜索历史邮件 | 每周 |
| S5 | 阅读带复杂排版的 HTML 邮件（营销、周报） | 每日 |
| S6 | 下载附件、预览图片 | 每周 |
| S7 | 断网状态下翻看已缓存邮件 | 偶尔 |

## 4. 信息架构与页面

### 4.1 主界面布局

采用 Mimestream 式三栏：**没有 App Rail、没有 Ribbon**，栏与栏之间不画分割线，只用背景明度分层（见 6.3）。

    ┌────────────────┬───────────────────────────┬──────────────────────────────┐
    │ 账户胶囊 ×2    │ 列表头：文件夹名 / 搜索 / 筛选 │ 阅读器工具条（悬浮，不占高）   │
    │ ─────────────  │ ───────────────────────── │ ──────────────────────────── │
    │ 文件夹 / 标签   │ 邮件列表 380px（320–窗口半）   │ 正文满宽 + 左右 32px 内边距    │
    │ 220px（折叠 50）│ 虚拟滚动，行高 26/60/88     │ 上下留白 24px                 │
    │ 底部：设置 / 同步 │                           │                              │
    └────────────────┴───────────────────────────┴──────────────────────────────┘

- 侧栏顶部是账户胶囊（Personal / Work），点击切换，右侧 `+` 添加账户。
- 列表与正文之间那条 1px 分隔线就是拖拽把手：可拖范围 320px ~ **窗口宽度的一半**（上限随窗口缩放，窗口变窄时自动收回），宽度持久化，双击复位 380px；侧栏可折叠为 50px 图标态。
- **侧栏只显示用户勾选过的文件夹**：侧栏底部有「选择文件夹」入口，点开扫描服务器上的完整文件夹清单（`folders:scan` → `refreshFolders`），勾选后才显示并参与同步；未勾选的不同步、不占侧栏，本地已下载的邮件保留。收件箱强制显示；新发现的系统文件夹默认勾选，新发现的自建文件夹默认不勾选（避免公司邮箱一连接就拉进一堆没用的目录）。升级前的历史文件夹全部保持勾选，不会突然消失。子项全部未勾选时，父容器分组也一起隐藏，不能出现「其他文件夹 > 其他文件夹」这种重复项（先按完整清单计算层级，再按勾选过滤）。
- 侧栏文件夹列表**占满底部同步/设置区以上的全部高度**（`flex-1 min-h-0`，超出时才在列表内部滚动）。不要用 `max-height: 45vh` 之类的固定上限——公司邮箱的个人文件夹很多，窗口明明还有空间时列表就被截断，用户只能盲目内滚找文件夹。
- 第二栏选中项与第三栏联动；第三栏可关闭进入双栏模式（P1）。
- 不设全局顶栏，搜索框以组合胶囊的形式**常驻标题栏中间**（没有搜索图标入口，也没有独立的搜索对话框）：左侧是范围下拉，右侧是输入框，输入即把当前列表切换成搜索结果。

### 4.2 页面清单

| 页面 | 类型 | 说明 |
| --- | --- | --- |
| 主界面 | 主窗口 | 三栏布局 |
| 添加账户 | 对话框（Dialog）/ 向导 | 3 步：邮箱地址 → 服务器参数 → 测试结果 |
| 设置 | 对话框（Tabs） | 外观 / 账户 / 同步 / 关于 |
| 搜索 | 标题栏常驻搜索胶囊 | 标题栏中间常驻组合胶囊，结果以列表筛选的形式呈现 |
| 同步状态 | 对话框（Dialog） | 只读：所有账户的连接/进度/文件夹游标/定时器 + 本次会话事件时间线；入口在侧栏底部状态行右侧 |
| 空状态 | 面板内状态 | 无账户、无邮件、无搜索结果、加载失败 |
| 通知 | 系统级 | Windows Toast |

### 4.3 同步状态面板

侧栏底部同步状态行**保留「点击 = 手动同步」**，行右侧另有一个 16px 的详情图标打开面板；侧栏折叠（50px）时整行只有一个图标，单击打开面板，手动同步走 `Ctrl+R`。

面板是**只读**的，打开它不能发起任何 IMAP 请求，也不能暂停/恢复定时器：

- 顶部：全局状态、上次同步、正在同步的账户数、下次轮询/对账倒计时。
- 账户卡：邮箱、服务器与加密方式、连接状态、错误原文、队列任务数、待推送已读、缺正文数；`error`/`disconnected` 时出现「重连」。
- 文件夹表：本地封数、最近一次看到的服务端封数、未读、回溯进度、当前忙碌状态；只列启用文件夹。
- 最近事件：渲染层保留本次会话最近 200 条同步事件，按时间倒序展示最近 80 条。
- 底部：日志路径与「打开目录」；自动刷新 1s（仅在面板打开时轮询）。
- 操作：立即同步、复制诊断、重连、打开日志目录。面板不提供修改同步参数的入口。
- 状态色：`primary`（正在连接/下载）、`success`（已同步）、`muted-foreground`（未连接/空闲）、`destructive`（错误）；状态必须带文字，不能只靠颜色。

## 5. 功能需求

### FR-01 账户接入（P0）

**描述**：用户手动填写邮箱地址、IMAP 主机、端口、加密方式、用户名、密码/授权码，点击"测试连接"，通过后保存。表单只有「自定义」一种形态，不做服务商预设。

> **只依赖收件服务器（IMAP）**：账户表单不出现 SMTP 字段，测试连接与同步也不探测、不校验发件服务器。发件服务器不通、端口被防火墙挡住、甚至根本没开，都必须能正常添加账户并收到信。

**规则**：
1. 默认端口 993（TLS），143（STARTTLS）。加密方式四选一：TLS（校验证书）/ STARTTLS（要求升级并校验证书）/ TLS · 忽略证书（仍然加密，跳过证书校验，给公司自签名证书用）/ 不加密。**「不加密」不等于跳过证书校验**，公司内网自签名证书应当选「TLS · 忽略证书」，否则用户会被「测试失败、保存后却能收信」误导。
2. 密码不写入数据库明文，使用 Electron `safeStorage`（Windows DPAPI）加密后单独存储。
3. **不做服务商预设**：本应用只服务公司自建服务器，表单直接呈现 IMAP 主机/端口/加密方式，不用选 QQ/163/Gmail/Outlook。默认端口 993、默认加密 TLS，主机留空由用户填。
4. 测试连接动作：TCP 连接 → TLS 握手 → LOGIN → 列出文件夹 → 断开，全过程 ≤ 15 s 超时。**测试连接与真实同步必须共用同一套连接参数**（`src/main/sync/connection.ts` 的 `buildImapOptions`）：早先测试固定校验证书、同步在「不加密」下不校验，导致测试报证书错误、保存后却能正常收信（用户 2026-11-23 实测）。错误文案必须给下一步动作（自签名 → 选「TLS · 忽略证书」或导入根证书；超时 → 检查端口与内网/VPN；STARTTLS 不可用 → 改 TLS 993），且完整展示、不截断。
5. 账户只保存 IMAP 相关配置，不保存 SMTP 主机/端口/凭据：本项目只收信，发件服务器不可达不构成任何失败（企业内网常见只有 993 通、25/465/587 被封的情况）。
6. 多账户并存：标题栏左段的账户胶囊点开是账户列表（当前项打勾，显示名称 + 地址），选中即切换；列表底部「管理账户…」进入账户管理弹窗。切换账户时文件夹树、列表、阅读器、未读数一起切到该账户，旧账户的选中邮件清空。新增账户保存后立即为该账户启动同步，无需重启。
7. **编辑账户**：账户管理列表每行有铅笔按钮，点开复用同一张表单（标题变成「编辑账户」，字段预填、密码留空表示不修改）。保存走 `accounts.update`，只有邮箱/主机/端口/加密方式/用户名/密码这类连接参数变化时才重启该账户的同步；仅改显示名不会重连。

**验收标准**：
- [ ] 输入错误密码时，5 秒内显示可读错误（区分：网络不可达 / 证书错误 / 认证失败 / 端口与加密方式不匹配 / STARTTLS 不可用）。
- [ ] 测试连接的结果与保存后的实际同步一致：测试通过则保存后能收信；测试因证书失败时，引导用户改用「TLS · 忽略证书」后测试通过。
- [ ] 163/126 邮箱在未发送 IMAP ID 时不应失败（内核自动发送 ID）。
- [ ] 保存后无需重启即可在文件夹树中出现该账户。
- [ ] 发件服务器（SMTP 25/465/587）完全不可达时，添加账户、测试连接、收信全部正常，不出现超时或报错。
- [ ] 两个账户可在胶囊里切换，切换后文件夹与邮件来自对应账户，不串数据。

### FR-02 文件夹（P0）

**描述**：连接成功后拉取文件夹列表，展示为树。系统文件夹置顶并映射到固定角色。

**规则**：
1. 文件夹名需处理 **modified UTF-7** 解码（中文文件夹名常见）。
2. 角色识别优先级：`\\Inbox` → inbox；`\\Sent` → sent；`\\Trash` → trash；`\\Junk` → junk；`\\Archive` → archive；其余为普通文件夹。
3. **未读数只以本地库为准**（`SELECT COUNT(*) WHERE is_read = 0 GROUP BY folder_id`），侧栏角标（默认显示未读数，可在设置里切换成显示文件夹的邮件总数）、列表页签「N 封」与列表标题共用同一份数据（标题栏不再重复显示未读数）。不要用 IMAP `STATUS (UNSEEN)`（服务器未读在与本地已读不同步时会偏大），也不要用「当前已加载的那一页」去数（那是 126 与 255 打架的原因）。标为已读时先乐观减一，IPC 返回后重新拉一次真实值；切换文件夹不得残留上一箱的数字（不闪旧值）。
4. 只读文件夹（`\\Noselect`，即容器目录）与普通文件夹**同款样式**，但不参与选中：整行只负责展开/收起，右侧给 chevron（展开 `ChevronDown` / 收起 `ChevronRight`），点整行或箭头都切换；不显示未读数。子文件夹每级缩进 14px、可正常选中，层级按路径段数递归。QQ 邮箱的 `其他文件夹/Steam`、`其他文件夹/QQ邮件订阅` 即此结构。侧栏折叠为 50px 时**只保留系统文件夹**（收件箱 / 草稿箱 / 已发送 / 垃圾邮件 / 已删除），自建文件夹（含「其他文件夹」下的子项）全部隐藏——50px 的图标栏既分不清层级，也认不出是哪个自建箱子；容器行同样省略。
5. 当前选中项若指向容器（服务器改了层级等），自动落回收件箱，不出现「列表空且无选中」的死状态。
6. **不做同名合并**：服务器上的普通目录与系统箱子可能只是名字像、实际是两个不同邮箱（UIDVALIDITY 不同），一律各自显示，不做按名字的过滤。为避免混淆，系统草稿箱的本地化标签是「草稿箱」，服务器自建的普通「草稿」目录原样保留。QQ 邮箱同时返回 `Drafts`（role=drafts，显示「草稿箱」）与 `草稿`（role=null，显示「草稿」）。
7. **`\Archive` 不提升为系统「归档」**：服务器上的「存档」等目录按普通文件夹处理，留在自建目录树里，避免同一个邮箱同时出现在系统区和自定义区。
8. **自建目录归组**：所有顶层自建文件夹（含服务器没给父容器的）统一收进「其他文件夹」分组，缩进一级显示。服务器给了 `\Noselect` 容器就用它当分组节点，没给就生成一个不可选中的虚拟分组。分组可折叠，折叠侧栏（50px）时省略分组节点。

**验收标准**：
- [ ] 中文命名的文件夹显示正确，不出现 `&UXZO1mWHTvZZOQ-` 这类编码串。
- [ ] 服务器上的每个可选文件夹都在侧栏出现且只出现一次（QQ 的 `Drafts` 显示为「草稿箱」、普通目录「草稿」独立显示，两者可分别打开且邮件不同）。
- [ ] 顶层自建文件夹（QQ 的「草稿」「存档」「QQ邮件订阅」）全部出现在「其他文件夹」下，不与系统文件夹混排。
- [ ] 未读徽标与实际未读数一致（±0）。
- [ ] 重复点击当前文件夹不会重新加载，列表不出现空骨架或空占位。

### FR-03 邮件列表（P0）

**描述**：按时间倒序展示当前文件夹邮件摘要。

**规则**：
1. **标准 / 宽松行结构**：行首 28px（宽松 32px）彩色圆形头像（首字母，见 6.3 第 7 条）。**标准默认只展示发件人与主题两行（行高 60px）；设置里开启「标准视图显示三行」后变成三行、行高 72px**——第一行 未读蓝点（6px）+ 发件人（13px/500，无则显示邮箱）+ 右侧时间；第二行 主题（14px，未读 600、`text-foreground` / 已读 400、`text-foreground/65`，单行省略）+ 右侧附件。**宽松（行高 88px）才是完整三行**——第一行同上；第二行 主题；第三行 摘要（13px、未读 `--muted-foreground` / 已读 `--muted-foreground`/65、单行省略）+ 右侧附件。时间格式：当天 `HH:mm`，本年 `M月d日 HH:mm`，跨年 `yyyy/M/d HH:mm`（标准/宽松默认在日期后带小时分钟，可在设置里关掉「非紧凑模式显示时分」只留日期；当天仍只显示 `HH:mm`。搜索面板固定用短格式，不受该设置影响）。
1.1 **紧凑行结构**（行高 26px，表格式单行，1:1 对齐 Foxmail）：不显示头像、摘要与三行堆叠，改为一行固定列——状态列（26px = 行首留白 8px + 18px 槽位，圆点居列正中）→ 附件列（18px，回形针，**与状态列各自独立**，不是共用一个槽）→ 发件人（默认 140px，单行省略，未读 500 / 已读 400 且降一档明度）→ 主题（自适应剩余宽度，单行省略，未读 600 / 已读 400）→ 日期（默认 68px 右对齐 `tabular-nums`，始终带时分）→ 大小（默认 52px 右对齐，`KB` / `MB` 单位，空值留白）→（紧凑视图没有星标列；置顶邮件不参与大小分组，统一排在最前，见 1.4）。状态列**每行都画一个 9px 圆点**（列头图例同尺寸）（仅紧凑模式）：未读为 `--primary` 蓝点、已读为中性灰点（`muted-foreground` 的低透明度，选中行也保持同一套颜色）；点圆点直接切换已读/未读，`stopPropagation` 不选中该行。每行底部有 1px `--table-line` 横向分隔线，用伪元素画且左右各内缩 8px——两端不与卡片左缘、右侧分隔线相交（2026-11-24 用户要求；选中行也保留，选中时靠底色区分而不是去掉线）；行内不设 `gap`，靠单元格 padding 对齐列头。
1.2 **紧凑日期列与列头**（Foxmail 口径）：列表顶部固定一行高 28px 的列头「状态 / 回形针 / 发件人 / 主题 / 日期 / 大小」，每列右侧有 1px 竖向分隔线（用 `.col-sep` 伪元素画，上下各内缩 6px，**不与横向表线相交**），列宽与数据行完全一致、不参与滚动，空列表不显示；**列头只取决于「有没有数据」，不能受 loading 控制**——刷新已有数据时若卸载列头，内容会整体上移 28px，表现成闪烁。**发件人 / 日期 / 大小三列可拖动分隔线调宽**：分隔线始终跟着鼠标走，把手都落在「可动的那条边」上——发件人列左边界挨着固定的 18px 回形针列、动不了，所以它的把手在**发件人与主题之间**那条线上（向右拖发件人变宽）；日期、大小的把手在各自**列名左侧**的线上（向左拖变宽）。三处命中区都是 6px，拖动时高亮为主色，鼠标离开把手后仍可继续拖（监听挂在 window 上）；宽度存 `localStorage["maildesk.compactCols"]`，双击分隔线恢复该列默认值；最小宽 56 / 72 / 48px（日期低于 72px「11-21 23:20」会折行，大小列同理，两列都设 `whitespace-nowrap` 兜底），最大宽度受列表宽度约束——拖到主题列只剩 96px 就停，列表整体被拖窄时自动收窄这三列。滚动条是浮层（见 6.3 第 8 条），不再占内容宽度，列头因此不需要为它让位；代码里仍保留 `offsetWidth - clientWidth` 的动态让位（浮层化后恒为 0），作为将来换回原生滚动条时的兜底。日期列当天显示「凌晨0:34 / 上午9:06 / 中午12:10 / 下午1:20 / 晚上8:15」，同一年显示「11-21 23:20」，跨年显示「2025-04-30」；**日期列被拖宽到放得下时自动带周几**（`11-19 (周四) 13:28`、跨年 `2025-04-30 (周三)`），放不下就退回原短格式——是否放得下用 canvas 按 12.5px 实际字体量「11-19 (周四) 13:28」的宽度，不要写死阈值；**日期与大小两列的字号（12.5px）和明度与主题列完全一致**（已读 /65、未读纯 `--foreground`（选中行不变白，仍按已读/未读取深浅）），不做第二档弱化；标准与宽松密度仍用原来的短格式（当天 `HH:mm`、本年 `M月d日`、跨年 `yyyy/M/d`）。选中行整行铺满（左边缘到列表右边）填充浅蓝 `--row-selected`、文字保持正常的已读/未读深浅（2026-11-24 用户指定），行为与标准密度一致。列头的「日期」「大小」都是按钮并按体积/时间分组：点「日期」按时间分组、点「大小」改成按体积分组（超大 ≥5M / 很大 1–5M / 大 500K–1M / 中 100K–500K / 小 25K–100K / 较小 5K–25K / 很小 <5K），再点当前列头在降序 / 升序之间切换（日期升序即从旧到新，大小升序即从 很小 到 超大，组内顺序同时反向）。**只有当前分组的列显示方向箭头**（降序 `ChevronDown`、升序 `ChevronUp`），另一列不画箭头；分组列不靠字体颜色标记，文字颜色与未分组时一致。组头条同样可折叠、可吸顶。
1.3 **日期分组**（三种密度都有）：邮件按日期分组，同一组连续邮件只在组首出现一次「组头条」——整行铺满列表宽度、高 24px（紧凑视图虚拟槽位 32px，**组头顶部留 8px 间距**把各组分开，2026-11-24 用户要求）、**紧凑视图是无底色无边框的纯文字行**（QQ 邮箱观感；**标准/宽松的组头保留原来的灰底圆角条**：`bg-muted/70`、悬停 `bg-muted/60`、常显上下箭头、半角 `(N 封)`、`font-medium`，2026-11-24 用户要求恢复）、`font-semibold` 加粗的 11.5px 文字「今天 / 昨天 / 本周 / 上周 / 两周前 / 三周前 / 上个月 / 更早」后面紧跟中文全角括号的 `（N 封）`（计数 `tabular-nums`、次要色）；展开状态不画箭头，仅折叠时左侧出现小 `ChevronRight`。组头条**滚动吸顶**（可在设置里关闭）：原组头滚出视口后，在列表顶部固定一条「当前组」的组头条（同样的名称 + `(N 封)`，点击可折叠），用实底 `bg-card` 盖住下方邮件行（组头条本身是透明的，吸顶条必须实底）；吸顶条不参与滚动高度（高度 0 的 sticky 容器），标准/宽松保留 `rounded-lg` 与左右内缩，紧凑保持全宽 + 下边框。分组在整箱邮件上计算，因此各组的 `(N 封)` 之和必须等于过滤行右上角的「N 封」。右键菜单里有「全部标为已读」（`Shift+U` 同效），一次 IPC 批量把当前列表里的未读清掉。组头可点击折叠/展开本组邮件行；**折叠状态按文件夹分别记忆**，在收件箱与已删除等文件夹之间来回切换时，各自的折叠状态保持不变（应用本次运行内有效，不落库，避免跨天日期分组变化后残留无效状态）。标准与宽松密度同样分组（设置里可关闭「非紧凑模式显示日期分组」），组头条改用与邮件行一致的 `rounded-lg` 圆角、不再画底部横线，并**只在下留 6px**（与组内第一封邮件、或下一个组头条；组行高按 24 + 6 = 30px 参与虚拟滚动）——组与组之间不再额外加上边距，上一项自己的 6px 下间距就是呼吸，避免「上一组最后一行 → 下一组头」被撑到 14px；紧凑视图是全宽表格，组头条保持 24px 全宽、不加间距，**也不画下边框**（纯文字行）。
1.4 **置顶组**（2026-11-25 用户要求，取代原来的「星标置顶」）：右键「置顶」/ `S` 把邮件标记为置顶（复用数据库里的 `starred` 列，库里列名不变），被置顶的邮件**不参与日期/大小分组**，而是单独成一组排在整个列表最前，组头标题固定「置顶」+ 封数，和其他组一样可折叠、可吸顶；取消置顶后回到原来的日期分组。置顶态不额外画星标图标，位置本身就是标识。
2. **必须虚拟滚动**，DOM 节点数恒定在可视区 + 10 行缓冲；行高随密度切换（紧凑 26 / 标准 60 / 宽松 88px），切换后需重新测量（紧凑的组头条高度 24px 也参与测量）。
3. **一次载入整个文件夹**：打开文件夹时一次从本地库取整箱（`ORDER BY sent_at DESC, rowid DESC`），不分页、不做滚动追加——本地库在连接账户后就是全量的，所以列表条数恒等于文件夹总数。首批到达前显示骨架屏；虚拟滚动保证 DOM 节点数恒定。
4. **右上角的「N 封」必须跟切换过滤条件一起换口径**，且只能是全量数字：全部 = 文件夹本地总数；未读 = 本地未读总数（与侧栏角标同一份 `unreadCounts`）；「有附件」目前没有全量统计，一律**不显示数字**（宁可留白，也不能拿「已加载那一页」的数字冒充全量）。过滤行整行高 44px（`h-11`），四个页签是 28px 高的圆角按钮（`h-7 px-2.5`），左右内边距 8px（`px-2`），与上下留白（(44−28)/2 = 8px）三边等距；数字右对齐贴边；这一行是列表顶部固定的工具区，不随邮件滚动。
5. 选中态与"已读态"分离：键盘移动不自动已读，停留 1.5 s 或点击才标记已读（防止误标）。自动已读**在每次选中开始时只排定一次**：选中时本来就已读的邮件，之后手动「标为未读」不会被这个定时器改回已读；手动标未读时还会取消仍在等待的定时器。
6. 支持按发件人聚合（P2）。
7. 空文件夹显示插画 + 文案，不显示空白。
8. **邮件行右键菜单**（与 Foxmail 对齐）：右键任意邮件行只**高亮该行并切换阅读器**，不标已读、不自动滚动；菜单项为「标为已读 / 标为未读（U）→ 置顶 / 取消置顶（S）→ 标为垃圾邮件 → 移动到…（子菜单）→ 复原（仅垃圾箱）→ 删除（Delete）」。垃圾箱里额外有「复原」：把邮件通过 messages:move 移回收件箱（role === "inbox"），保留原 id、正文缓存与已读态；本项目不记录「原文件夹」，复原一律回收件箱，UI 不要暗示能回到原子文件夹；找不到收件箱时提示「复原失败 · 找不到收件箱」。移动到子菜单复用侧栏命名（排除 `\Noselect` 容器与当前文件夹）；标为垃圾邮件即 `messages:move` 到 `role === "junk"` 的文件夹，当前已在垃圾箱/垃圾邮件时该项隐藏；垃圾箱内的「删除」显示为「永久删除」。菜单项复用列表与阅读器的同一套 handler，失败提示同 FR-04 规则 8。「移动到…」「复原」「删除」都作用在**整份选中集**上：右键点的那行在当前多选集合里就整批处理，否则只处理该行（Foxmail 同款）；只传单 id 会让 `Ctrl+A` 后从右键菜单删一次只掉一封。暂不提供「标签」——没有标签系统。
9. **多选**：`Ctrl/⌘ + 点击`在选中集合中增减一行，`Shift + 点击`从当前活动行到点击行整段选中（不标已读），普通点击清空多选回到单行；`Ctrl+A` 无条件生效：选中**整个当前文件夹**（不受「未读 / 有附件」页签限制，并自动切回「全部」，让每一行都可见地变成蓝底），无需先选中一封；同时阻止浏览器选中页面文本。多选与全选都**不标已读**（避免批量选中把一堆未读变成已读），也不触发「停留 1.5 秒自动已读」。`selectedId` 仍是其中的活动行，决定阅读器内容与滚动定位；行底色由 `selectedIds` 集合决定（集合为空时才回落到 `selectedId`），不要只比 `selectedId`——否则 `Ctrl+A` 集合已全选，界面却只亮一行，看起来像没反应。多选态下 `Delete` / `Backspace` 批量删除（垃圾箱内为永久删除）并收起多选，`J/K` 上下移动会收敛回单行。
10. **滚动位置只在换文件夹 / 换过滤条件时归零**：删一封（或一批）邮件后，列表必须停在原处，不能跳回顶部，也不能整块刷新闪烁。因此：回顶部的 effect 只依赖 `folderId` 与 `filter`，**不能依赖 `messages[0]?.id`**（删掉首行也会变，等于每删一封就归零）；删除/移动成功后**不再整箱重取**——本地 filter 就是终态，只有部分失败（IPC 只回计数，界面猜不出是哪几封）才回库兜底；主进程的本地变更回执（`messages` 事件且 `added === 0`）只刷计数、不重拉列表，避免一次删除触发两个加载周期；刷新已有数据时不要切骨架屏——骨架会清空滚动容器的内容高度，`scrollTop` 会被浏览器夹到 0，只有「没有任何邮件」时才显示骨架（`loading && messages.length === 0`）。

**验收标准**：
- [ ] 10,000 封邮件滚动无明显掉帧（DevTools Performance ≥ 55 fps）。
- [ ] 切换文件夹时列表不出现内容闪烁（保留骨架屏 ≤ 200 ms）。
- [ ] 时间格式化符合上述规则，跨天/跨年边界正确。

### FR-04 阅读器（P0）

**描述**：渲染选中邮件的头部信息、正文与附件。

**规则**：
1. 正文区任意位置右键 = 和列表行完全相同的邮件菜单（标为已读/未读、全部标为已读、置顶、标为垃圾邮件、移动到…、复原、删除）；HTML 正文在 iframe 里，右键由同源监听换算坐标后转发给正文区，不额外做一套原生菜单。头部：主题（大字号）→ 发件人区（左侧头像与右侧两行信息**整体垂直居中**；第一行发件人姓名 + 操作图标组（置顶、标记未读、保存全部附件、「移动到」下拉、删除），第二行邮箱地址 + 完整时间）→ 收件人/抄送（折叠态只有一行摘要：≤3 人时列全名；人多时「发给 甲、乙 等 N 人」，有抄送再追加「· 抄送 M 人」，整行 `truncate` 不换行。点开是浅色面板：发件人一行 +「收件人 N」「抄送 M」两组联系人。**每行只显示一位联系人**：姓名与地址在同一行，姓名近黑且保持完整不省略，地址用去掉尖括号存储、展示时包成 `&lt;address&gt;`、次要色（超长时只在括号内省略，`title` 给完整 `姓名 <地址>`）；显示名整段同色，不要按「/」拆段加粗或改色，无姓名时只显示地址；**姓名必须从 To/Cc 原始头解析**（同步时随 `headers: ["to","cc"]` 取回，RFC2047 解码），因为 QQ 等服务器的 ENVELOPE 会把 personal name 填成地址本地部分，单组最高 260px 内部滚动。公司邮件常见几十个收件人，**不能**再用「、」把全部地址拼成一堵墙）→ 标签与附件 chip → 正文。**不再有独立的 52px 工具条**，图标与发件人同行后正文整段上移，`article` 顶部只留 20px（`pt-5`）。图标组**最右侧**是「该发件人的全部邮件」抽屉按钮：点开右侧 320px 抽屉，头部显示发件人头像、姓名与邮箱地址（不再写「该发件人的邮件」这类说明文案）；按发件地址跨文件夹列出这个人的全部邮件（未读点、主题、完整时间，不显示正文摘要，当前这封高亮），点击任意一条即切到对应文件夹并选中打开。**没有关闭按钮**：点抽屉外的任意空白处收起（透明遮罩，不加暗色），`Esc` 与换一封邮件也会收起。时间格式 `yyyy年M月d日 周X HH:mm`（周三这类「周X」写法，不用「星期三」）。
2. 正文渲染优先级：`text/html` → 沙箱渲染；无 HTML 则 `text/plain` → **画布直排、不套卡片**，按空行分段、块内保留换行与缩进（`whitespace-pre-wrap`），行宽 `max-w-[76ch]` 左对齐、不做版心居中，长 URL 与长单词 `break-words`；整块以 `>` 开头的引用用左侧 2px 竖线 + 12px 缩进、次要文字色，同样不画卡片。
3. HTML 安全：
   - 使用 DOMPurify 清洗，移除 `script`、`iframe`、`object`、`form`、事件属性、`javascript:` 协议。
   - 渲染于**禁用 Node 集成的独立 BrowserView/iframe sandbox**，或 `<webview>`（选型见 7.3）。
   - 强制注入基础样式：图片 `max-width: 100% !important; height: auto`、`table { max-width: 100% }`、单元格内长单词 `overflow-wrap: break-word`；**不覆盖 `td/th` 的内外边距**，也不做全局 `max-width` 钳制——银行/营销邮件的定宽单元格会被压窄导致数字折行。
   - 保留邮件自带的内容区背景色（表格 / 单元格 / 卡片的 `bgcolor`、`background`、`background-color`）与 `<style>` 块（iframe 沙箱隔离，只作用于邮件文档）；去掉它们会丢掉横幅、分隔线与表格宽度。**页面级背景（`body` / `html` / 正文第一层的页面底色）不显示**：阅读区就是容器（2026-11-24 定稿），见下一条。**`<head>` 里的 `<style>` 必须保留**：DOMPurify 默认只返回 body 内容，`<head>` 会被整块丢掉，字体族、字号、行高、媒体查询与 `body` 背景随之失效（2026-11-24 实测：457 封里 189 封把样式写在 `head`，只有 33 封写在 body 内）。清洗必须带 `WHOLE_DOCUMENT`，再把 `head` 的 `<style>`（含 `media` 属性）搬进最终文档的 `head`，顺序在应用基线样式之后，让邮件自己的规则优先生效；`<html>` / `<body>` 上的 `style`、`bgcolor`、`background`、`class`、`dir`、`lang` 也要合并到最终文档，否则页面底色与按 `class` 选择器写的样式全部失效。
   - **统一容器（2026-11-24 定稿）**：不再保留邮件自带的「页面容器」——`body` / `html` / 正文第一层的 `bgcolor`、`background`、`background-*` 一律清掉，基线 CSS 用 `html, body { background: transparent !important }` 兜住写在 `<style>` 里的页面底色；内容块自己的底色（卡片、单元格）保留。同时把**页面级定宽**改成百分比：内联 `style` 与呈现性属性 `width` 中 ≥480px 的一律 `width/max-width: 100%`（`min-width` 归零；属性值可能写成 `660px` / `585.0`，按前导数字判断），`<style>` 里的 `width: 640px` / `.mj-column-px-640 { width: 640px !important }` 也一并改写（`fluidWidths()`）——否则 MJML 邮件的 900px 卡片在 1080p 小屏上只能横向滚动、右侧文字被截断（用户实测）。480px 以下的定宽（分栏、按钮、图片）不动。用 `setProperty` 时必须写 kebab-case（`max-width`），写 camelCase 会被静默忽略。
   - **基础样式里也不要再给 `html` / `body` 声明其他 background**：`bgcolor` / `background` 属于呈现性提示，优先级低于作者样式；统一容器模式下页面底色一律由阅读区提供。
   - **文本优先渲染（不做整页缩放、不套「印刷品」白纸卡片）**：公司邮件常带固定 slogan 图与 660px 级定宽表格，旧做法把整页 `zoom` 缩到 0.6 并塞进 720px 白卡片，等于把每封邮件显示成一张缩小的截图，小字根本看不清（用户 2026-11-23 实测否掉）。现在 iframe **自身背景透明**、直接落在阅读画布上（邮件自带的页面底色不显示，内容块的底色保留），**正文**（HTML 或纯文本）外面有一个**直角矩形容器**（无边框、无圆角、上下内边距 20px、**左右由 `article` 的 24px 统一控制**，最宽 900px；2026-11-24 用户要求去掉那圈 1px 直角框，并按 QQ 邮箱实测把正文到画布边缘的边距改成 24px），只标出正文容器范围；主题、发件人、收件人、附件 chip 都在卡片之外（用户 2026-11-24 定稿）。卡片左对齐（**不居中**，窗口变宽时内容不往中间挪，只是右侧多出空白），随阅读区宽度回流，超宽屏不会把一段话拉成两三千字一行；**卡片高度撑满阅读区剩余高度**（`article` 是 `flex min-h-full flex-col`，正文卡片 `flex-1`），内容短时也一直延到窗口底部，长正文再随内容继续长高；默认字色固定 `#242424`，链接色固定 `#1a5fd0`；邮件自带的浅色底、底图仍原样保留。**字体与源邮件一致**：保留邮件自己的 `font-family` / `font-size` / `font-weight`，不做字号下限或加粗；只对直接承载文字的节点做对比度兜底（与有效背景 < 3:1 时改成主题前景色，遇到 `background-image` 底图则跳过）。**Excel 粘贴的表格**（table 带 border 属性或单元格带边框样式）标记为 `data-maildesk-table`，铺白底 + `border-collapse: collapse`，保留 Excel 的边框、底纹、对齐与字体；布局用隐形表格不受影响。**不再有 `zoom` 缩放**：超宽的定宽表格由 iframe 自身横向滚动，宁可横滚也不把整封邮件缩成小图。
      - **不放任邮件自造的小滚动框**：营销/通知邮件常用「固定高度 + `overflow:auto/scroll/hidden`」做内嵌小窗，阅读区明明有空间却只能在 250px 里滚（用户 2026-11-24 要求）。渲染时统一放开：先按内联 `style` 把 `height` / `max-height` 改成 `auto` / `none`（高度 < 24px 的跳过，那是 preheader 隐藏块的惯用写法），正文加载后再按计算样式兜一次（覆盖类选择器与带 `!important` 的规则），条件是「`overflow-y` 为 auto/scroll/hidden、元素高度 ≥ 24px、且 `scrollHeight` 超出 `clientHeight`」。
- **滚动条只属于阅读区**（用户 2026-11-24 要求）：iframe 带 `scrolling="no"`，正文文档 `html, body { overflow: hidden }`，邮件内部再出现纵向/横向滚动条都算 bug。宽度靠四条规则压进阅读区：① ≥480px 的页面级定宽（内联、`width` 属性、`<style>` 规则）改 100%；② 表格列宽（`<col>` 或首行单元格）按「宽 / 总和」换算成百分比，`table-layout: fixed` 的大表等比缩到阅读区；③ 图片 `max-width: min(100%, 100vw)`，防止 float / shrink-to-fit 容器里按原始像素撑破布局；④ 超出阅读区的 `nowrap` / `text-wrap: nowrap` 文本放开换行（猎聘那封 1033px 的大标题就是靠它把整页撑到 1075px）。四条规则之后仍然压不进去的极宽内容（超宽表格、巨图）**不再裁掉，改为允许阅读区横向滚动**：`HtmlBody` 检测到内容宽于 iframe 时把 iframe 撑到内容宽度、并临时放开 `overflow` / 900px 版心，横向滚动条由**阅读区的原生滚动条**承担（2026-11-25 起阅读器正文改用原生滚动条，样式套 `.scrollbar-native` 与浮层细条一致；列表等其他容器仍是浮层细条），邮件内部依旧没有自己的滚动条。
- **高度自适应**：iframe 高度取内容实际高度（body 盒高与文档滚动高的较大值），图片加载、窗口缩放时用 `ResizeObserver` 重算，正文底部不留大片空白。
   - **失效图片与追踪像素**：加载失败的 `<img>` 不允许显示浏览器默认的碎图图标。声明尺寸 ≤ 2px 的（0×0 / 1×1 追踪像素，常见实现是返回 1 字节的“图片”）直接 `display:none` 不占位；有正常声明尺寸的失败图**整体替换成同尺寸的占位 `<div>`**（浅灰底）并保留原尺寸——只删 `src` 不够，空 `<img>` 浏览器照样会画碎图图标。QQ/Apple 这类客户端要么走图片代理，要么直接隐藏失败图，不会把 Chrome 的破图图标暴露给用户。
3.5 **正文版式（固定原版式）**：不再提供「正文适配方式」设置项。页面底色、定宽、字体、图片尺寸全按源邮件，**不缩放也不压宽**，超宽内容（定宽版式、宽表格、大图）由阅读区横向滚动条接手，绝不裁剪。实现上先按阅读区宽度排一遍量出 `scrollWidth`，再用「元素上写死的最大宽度（`width` 属性或内联 px，≥240px）」推定设计宽度，取 `width = max(pane, design, laidOut)` 铺开 iframe，高度按该宽度实测；不含 `transform: scale`，右键坐标 1:1 换算。旧的重排（`reflow`）与整封等比缩放（`zoom`）均已删除，不要恢复对应设置或渲染分支。
4. 远程图片：默认**放行**（`remoteImages: true`）；设置为拦截时替换为占位块，顶部提示"已拦截 N 张远程图片 [显示图片]"，点击后本次会话放行。**拦截态必须在邮件文档里注入 CSP**（`default-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src data:; script-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`）——只替换 `<img>` 堵不住 `<style>` 里的 `@import`、`background-image: url()` 与 `@font-face`，营销邮件仍能靠这些通道回传「谁在什么时候打开了信」。放行态只放开 `img-src` / `font-src`，脚本与外部样式表永远不放。`cid:` 内嵌图片在同步时随正文一起取回并转成 data URL 嵌入（单张 ≤10MB 编码尺寸、整封 ≤16MB 解码合计），正文里的截图直接可见；超过上限、取不到或老数据才回退透明占位 + `alt="内嵌图片"`，不要显示碎图标。**上限必须能覆盖「整封 2MB 以上的纯图片宣传邮件」**：`image.size` 是 base64 后的尺寸，2MB 的图对应约 1.5MB 原图，旧上限会让这类邮件整封空白（2026-11-26 用户实测）。
5. 附件判定：**正文内嵌图不算附件**——`multipart/related` 里带 `Content-ID` 的图片、或 `Content-Disposition: inline` 的图片，既不挂回形针也不生成附件 chip（营销邮件把配图写进正文的情况很常见）；只有真正的附加文件才计入「有附件」。正文用 `cid:` 引用的内嵌图属于正文的一部分，同步时一并取回（不算附件、不挂回形针）。
6. 附件交互：**左键单击附件 chip = 打开**（图片弹内联预览层，其他类型先下载到 `temp/maildesk-attachments` 再用系统默认程序打开）；**右键 chip 出菜单：打开 / 保存… / 保存全部…**。下载时 chip 上显示百分比（主进程按 120ms 节流推 `attachments:progress`，进度拿不到总大小时仍显示 spinner）。`attachment.part` 在正文解析时记下 BODYSTRUCTURE 的 part 号，保存/预览/打开直接按它取那一段，省掉每次一次的 `fetchOne` 结构查询（老数据没有 part 时自动回退）。**固定渲染在发件人信息下方、正文之上**（写在 `Article` 头部的 `Chips` 区），长正文时不必滚到底也能看到；展示文件名、大小、类型图标；非图片点击即弹保存对话框；图片先弹内联预览层，预览层内可再保存；**预览层的关闭条件必须覆盖「加载中 / 加载失败 / 已加载」三种状态**——只清 `preview` 会把错误提示永久钉在屏幕上（实测点开非图片附件后整窗卡死），所以统一走 `closePreview()`（同时清 `preview`/`previewError`/`previewBusy`），Esc 与点击浮层空白处同样生效；是否走预览只看 MIME 前缀 `image/` 或图片扩展名，**不能**用列表图标分类 `Attachment.type`（压缩包是 `application/octet-stream`，会被服务端拒绝）；保存状态在 chip 上以 spinner/对勾反馈，用户取消视为无操作，失败标红。工具条「保存全部附件」一次选目录，同名文件自动追加序号不覆盖。附件 chip 与标签 chip **同一行**（`flex-wrap`，标签在前、附件在后，统一 `h-5` 胶囊高度）；附件多时换行，超过 3 个折叠为「+N 个附件」。
7. 编码：解析失败回退 `iconv-lite`（GBK/GB2312/GB18030 常见于国内老邮件），仍失败则展示"无法解码"并允许查看原始源码。
8. 移动与删除（工具栏，按钮文案随所在文件夹变化）：
   - 「移动到」下拉列出侧栏里所有可选中文件夹（复用侧栏命名，排除 `\Noselect` 容器与当前文件夹）；选中后立即调用 `messages:move`，本地行随服务器 MOVE 改到目标文件夹并保留 id/正文缓存/已读态。
   - 「删除」在普通文件夹是**移到垃圾箱**（`role === "trash"` 的文件夹）；已在垃圾箱里时变成**永久删除**（EXPUNGE），按钮 title 相应变为「永久删除 (Delete)」，不弹二次确认，靠垃圾箱本身兜底。
   - 两个操作成功后都从当前列表移除该行、清空阅读器、刷新文件夹计数与未读数。
9. 操作失败反馈：移动/删除是「服务器先行」——服务器不可达或被拒绝时本地不变，**不能静默吞错**。失败时在窗口底部居中弹出一次性提示条（~Notice~：红色警示图标 + 一句话原因，3.5 s 自动消失，不打断阅读）。错误串按关键词归一成人话：含 ~network~ →「网络未连接，请稍后重试」，含 ~auth~ →「账户授权失效，请重新填写密码」，含 ~not-found~ →「目标文件夹已不存在」，其余取最后一个 ~Error: ~ 之后的内容。~result.failed > 0~ 时也按同样方式提示。
10. **链接与引用**：页内 `#` 锚点交给 iframe 自己滚；`http(s)`、协议相对 `//`、`mailto:`、`tel:` 交给系统打开（主进程白名单同步放开）；其余（相对路径、`file:`、`javascript:`）一律 `preventDefault`，邮件不能把应用导航走。长线程的引用历史按 `blockquote` / `.gmail_quote` / `#divRplyFwdMsg` / `.yahoo_quoted` 识别（只取最外层，高度 > 260px 或文字 > 500 字），折叠成「显示引用内容（N 字）」横条，点击展开/收起——Gmail、Apple Mail、Outlook 都是这个行为。

**验收标准**：
- [ ] 带 slogan 图与 660px 定宽表格的公司邮件：正文不再被整页缩小，文字保持设定字号；超宽部分只在正文内横向滚动。
- [ ] 浅色主题下打开浅色底板邮件（如银行账单），邮件自带底色与横幅完整、文字清晰；没有自带底色的邮件自动用主题前景色，不出现深字压深底。纯文本仍旧画布直排、不套卡片。
- [ ] 正文高度贴合内容，末尾不留大片空白（图片加载后也不出现纵向内层滚动条）。
- [ ] 含 `<script>alert(1)</script>` 的邮件不弹窗、不执行。
- [ ] GBK 编码邮件正文中文正常显示，无乱码。
- [ ] 拦截远程图片时，含 CSS 追踪（`background-image` / `@import`）的邮件在 DevTools Network 里没有任何外部请求。
- [ ] HTML 长线程默认折叠引用历史，点「显示引用内容」能展开，展开后正文高度随之重算。
- [ ] 断网后点「删除」不再静默无反应：底部提示「删除失败 · 网络未连接，请稍后重试」，列表与服务器均无变化。

### FR-05 同步引擎（P0）

**描述**：后台持续把 IMAP 邮件增量落库，并通过事件通知 UI。

**规则**：
1. **只同步用户勾选的文件夹**：`syncAll` / 历史回溯 / 对账 / 正文补齐都只处理 `folder.enabled = 1` 的文件夹；未勾选的文件夹不建游标、不拉历史、不下载正文，托盘未读数也只统计启用文件夹。`refreshFolders` 仍然扫描服务器全部文件夹并写库（否则弹窗里看不到它们），但不覆盖用户已有的 `enabled` 选择。
2. **连接账户后无条件全量下载（已勾选文件夹），并且正文一起落库**：不做「全部 / 最近 N 封 / 不自动」这类策略，也不做按需的渐进式加载——首屏先取最近 200 封（`pageSize`）让界面可用，其余历史由后台回溯循环一路补到服务端最后一封；每批 200 个 UID，先取 `envelope/flags/internalDate/size/BODYSTRUCTURE`，随后按结构里的正文 part 号批量取回 `text/plain`、`text/html` 与内嵌截图（带 Content-ID 的 image part，单张 ≤10MB 编码尺寸、整封 ≤16MB 解码合计；真正的附件二进制不取），批间间隔 120 ms。**点开邮件不再请求服务器**：正文、摘要、附件元数据在同步时就已完备，`fetchBody` 只作为老数据的兜底（正文补齐循环会把它们也补上）。老版本懒加载留下的空正文由启动时的 `bodyBackfillLoop` 逐批补完。
   - 回溯游标 `folder.backfill_uid` 持久化（下一批的上界），**不能**用 `MIN(uid) - 1` 推算——服务端 UID 有空洞（删除过邮件），空批次会让 `MIN` 原地不动而死循环；每批无论命中与否都必须把游标推进到 `from - 1`，`< 1` 表示翻到底，`null` 表示还没开始。
   - 进度通过 `SyncEvent { type: "backfill", folder, done, total, finished }` 推给 UI，侧栏同步文案显示"补全历史 N / M"。
   - **首次连接必须可见地「在动」**：连接阶段显示「正在连接服务器…（Ns）」，下载阶段显示「正在下载 收件箱 50 / 200」，正文预下载显示「正在下载正文 N / M」，历史回溯显示「补全历史 N / M」。列表还没有邮件时，空态换成「首次同步进行中」+ 当前进度，绝不能显示「这个文件夹还是空的」。`SyncStatus` 里带 `startedAt` / `progress` / `bodies` 快照，界面晚于同步启动（重载、切账户）也能立刻恢复进度。
3. 增量：记录 `last_synced_uid`，每次 `UID SEARCH UID (last+1):*`。
4. 实时：对 INBOX 建立 IDLE 连接，收到 `EXISTS` 后触发增量拉取，**不重新登录**。
5. `UIDVALIDITY` 变化 → 清空该文件夹本地数据 → 全量重拉（必须有明确日志）。
6. 断线：指数退避重连（1s → 2s → 4s … 上限 60s），连续失败 3 次在 UI 顶部显示"离线"状态条。
7. 解析在**主进程**完成。同步时按 BODYSTRUCTURE 精确取正文块（`text/plain` / `text/html`）解码落库；只有老数据回退到 `fetchBody`（`source.maxLength = 512 KB` 的整封兜底）。
8. 并发限制：同一账户同一时刻只允许一个同步任务，多账户可并行。
9. **双向对账**（启动时一次 + 每 3 分钟一次，`reconcileAccount`）：对每个已同步文件夹枚举服务器全箱 UID 与本地比对，抹平两侧差异：
   - 服务器有、本地无 → 补拉（头部 + BODYSTRUCTURE，正文同批预下载）；
   - 本地有、服务器无 → 服务器已删或已移走：若别的文件夹出现同 `Message-ID` 的邮件，用 `moveMessageRow` **认领**本地旧行（id、正文缓存、已读态全部保留），否则删本地行；
   - 服务器已读标志与本地不同 → 回写本地（刚点过、还在 `pendingFlags` 队列里的跳过，避免被旧状态覆盖）；
   - 每个文件夹上限 20 000 封，超过则跳过并 `console.warn`。
10. **启动顺序**：`refreshFolders → reconcileAccount → syncAll`。必须先对账再增量，否则被网页版/手机 MOVE 走的邮件会被 `syncAll` 当新邮件重新插一行、旧行再被对账删掉（实测丢过 id）。
11. **文件夹也双向**：`refreshFolders` 放在 `reconcileAccount` 开头，所以启动、手动同步、每 3 分钟对账都会重读服务器文件夹清单；服务器上已经不存在的文件夹（网页版/手机端删除）连同本地邮件一起删掉（`deleteFolder` 先显式 `DELETE FROM message WHERE folder_id = ?`，因为外键级联删除不触发 message 的 `AFTER DELETE` 触发器，FTS 会留残影），并打 `[sync] folder removed <email> <path>`。侧栏当前选中的文件夹若被删掉，文件夹清单刷新后自动落回收件箱。**删掉文件夹时必须让 `reconcile` 事件照常发出**（`added/moved/removed/flags` 全是 0 也要发），否则渲染层收不到刷新信号，启动瞬间拉到的旧文件夹清单会一直挂在侧栏上（实测）。
12. 增量拉取偶发取不到某封的头部时（QQ 存在这种"幽灵 UID"），`last_synced_uid` 仍会推进；该封由下一轮对账补回，不靠游标回退。
13. **附件尺寸必须取自 BODYSTRUCTURE，不能取自被截断的正文**：正文预下载只取正文与内嵌图片 part，真正的附件二进制不在同步时传输；兜底路径 `fetchBody` 只取整封前 512 KB，mailparser 对截断的附件给出的 `size` 只是残片长度（实测 40 MB 的附件报 369 KB），所以两条路径都用 `collectAttachmentParts()` 各 part 的 octets 覆盖尺寸；base64 要按 76 字符一行折算（`(size − 行数×2) × 3/4`），直接乘 0.75 会偏大 3%（40 MB 显示成 41.1 MB）。
    - 口径差异（不是 bug）：列表「大小」列是整封信的 RFC822 字节数（`envelope.size`，含 base64 膨胀与全部头部），附件 chip 是解码后的文件大小，两处数字本来就不会相等。
14. **永久删除（EXPUNGE）必须复查结果**：QQ 对多 UID 的 `UID STORE +FLAGS \Deleted` / `EXPUNGE` 不可靠——实测一次删 3 封只掉 1 封，函数不报错，剩下 2 封留在服务器上；本地行却已经删掉，下一轮对账又把它们拉回来，用户看到的就是「全选后只删了一条」。所以 `purgeByFolder` 先整批 `messageDelete`，再按 UID `fetch` 复查一次，把剩下的**逐封补删**，最后只对确认消失的邮件删本地行，并把没删掉的数量计入 `failed`（界面据此提示「删除失败 · 服务器拒绝了其中 N 封」）。

**验收标准**：
- [ ] 新邮件到达 ≤ 3 s 内出现在列表顶部（IDLE 生效）。
- [ ] 手动修改服务器 `UIDVALIDITY`（模拟）后，客户端日志出现重同步且数据不重复。
- [ ] 拔网线 1 分钟后恢复，自动重连并补齐期间邮件。
- [x] 历史回溯：把本地 INBOX 最早的 100 封删掉后后台自动补回（隔离库实测 373 → 473，服务端 474）。
- [x] 服务器删除 → 本地删除：网页版删掉一封后，下一轮对账日志 `removed 1`，本地行消失。
- [x] 服务器移动 → 本地认领：网页版把邮件移到子文件夹后日志 `moved 1`，本地行 id 不变、只改 folder 与 uid。

### FR-06 搜索（P1）

**规则**：
1. 标题栏中间**常驻**一个搜索组合胶囊（高 24px）：左侧是范围下拉（**发件人 / 收件人 / 标题 / 正文**），右侧是输入框；没有搜索图标入口，也不弹任何候选窗口/遮罩。`Ctrl+K` 或 `/` 把焦点送回输入框，`Esc` 清空关键词。
2. **结果就是列表**：输入关键词后，列表数据从「当前文件夹」切换成跨文件夹的搜索结果（按时间倒序），搜索胶囊本身不展示任何结果；清空关键词即回到当前文件夹。搜索时筛选页签（全部/未读/有附件）继续作用于搜索结果，右上角「N 封」显示结果条数。
3. 范围搜索走主进程 `searchMessages(q, { scope })`：`from` 匹配发件人姓名/地址，`to` 匹配收件人与抄送（`to_json` / `cc_json`），`subject` 只匹配主题，`body` 只匹配正文纯文本；不传范围才走 FTS5 全字段。范围查询用 `LIKE` 字面量匹配并转义 `% _`，因为 FTS5 的 `unicode61` 会把整段中文当成一个 token（「信用管家」搜不到「每日信用管家」）。
4. **命中关键词高亮**：按当前范围只在对应字段标 `<mark>`——发件人 → 发件人列，标题 → 主题，正文 → 摘要；收件人不在列表展示所以不高亮。底色统一用 `primary/25`（选中行也是，2026-11-24 起选中行不再变白）。按输入的字面量做大小写不敏感匹配，不做正则/多词组合。
5. **紧凑视图的搜索结果在表格最后多一列「所在文件夹」**（默认 92px，列内右对齐、左缘截断；**列头左侧的分隔线就是拖拽把手**，向左拖加宽、双击恢复默认，宽度存进 `maildesk.compactCols`；普通文件夹视图不显示，标准/宽松也不显示）。
6. 切换文件夹或点击标签会清空关键词，列表回到该文件夹；搜索结果里移动/删除/标已读仍走同一条 IPC，永久删除与否按该封邮件自己所在的文件夹判断。

**验收标准**：
- [ ] 10,000 封库内搜索响应 < 150 ms。
- [ ] 中文分词可用（至少支持按字/词的子串匹配，FTS5 使用 `unicode61` + trigram 或 `simple` 分词器）。

## 6. UI / UX 规范

### 6.1 设计方向：Quiet Light

方向代号 **"Quiet Light"**：**结构取 Mimestream**（三栏、去边框、大留白、胶囊切换，颜色只用于状态），**配色取 QQ 邮箱**（标题栏/侧栏 `#E6EDF5`、画布纯白）。**只维护浅色一个主题，不提供深色模式**（2026-11-24 决定）。

1. **去 chrome**：不使用分割线、Ribbon、App Rail。层级只靠背景明度、字重与留白表达。
2. **明度分层**：标题栏/侧栏 → 画布 → 浮面 → 选中，靠明度差表达层级，不堆边框；大面积不使用纯黑。
3. **字重优先于颜色，明度分层表达已读**：未读/已读先靠 `600` 与 `400` 区分，再让整行明度**轻轻**差一档——已读行的头像（`opacity-60`）、发件人（`text-foreground/70`）、主题与日期/大小（`text-foreground/65`）、摘要与时间（`text-muted-foreground/65`）一起变淡，未读行保持纯 `--foreground`，扫列表时未读自然浮出。这个档位是用户明确要求「已读再暗一档、提高反差」后定的：早期试过 `/60` 觉得糊、后来收到 `/80` 又觉得反差不够，**以 /65–/70 为准**；再暗就会伤可读性，再亮就拉不开层次。颜色仍只留给品牌蓝、置顶、标签，不要给已读行染灰蓝色调。
4. **克制动效**：仅用于状态变化，120–160 ms `ease-out`，只动 `opacity` 与 `transform`。

1. **选中行**：浅蓝 `--row-selected`（`#DBEBFD`）填充，但用**左右内缩 8px、上下内缩 2px 的圆角伪元素**画（不铺满整行；hover 同理用 `--row-hover`），主/次级文字保持正常的已读与未读深浅（**不再转白**，2026-11-24 用户指定）；行高不变，不做缩放。
2. **悬停**：全应用统一取列表的 hover 色 `--row-hover`（`#F3F4F6`），选中统一用 `--row-selected`（`#DBEBFD`）；不再用 `foreground/[0.0x]` 叠层画 hover，不位移、不加阴影。**侧栏例外**：文件夹项仍用 QQ 的那套 `--nav-hover` `#DBE3ED` / `--nav-selected` `#C6DCF4`（2026-11-24 用户要求保留）；**标题栏控件例外**：账户胶囊与折叠 / 密度 / 下载 / 窗口三键的 hover 用 `foreground/10` 的中性灰（`#F3F4F6` 在浅蓝灰底上看不出来）。
3. **阅读器正文**：直接落在白色画布上，不套卡片、不画外框；左右内边距 24px。**页头与正文之间有一道 1px 分隔线**（`--table-line`，只在正文存在时出现；线到页头 16px、到正文首行 16px，2026-11-24 用户要求），HTML 内容按文本优先渲染。
4. **列表行之间不画线**，靠 8px 垂直间距与留白分隔。
5. **分割线**：仅在列表与阅读器之间保留 1px `--border`（`#CDCDCD`）；侧栏与画布之间用明度差区分，不加线。
6. **标签胶囊**：底色为标签色 18% alpha，文字为该色提亮 20%，高 20px，圆角 999px。
7. **头像**：首字母（英文取首字母大写，中文取首字）+ 由名字 hash 出的固定底色，白字 600。色盘 8 色：`#6D5AE6 #2F9E6E #E08A3C #2E6BFF #C0567F #23879B #A855C7 #B08A3E`，同一个人永远同色。尺寸随场景：列表 28 / 32px（对应标准 / 宽松）、阅读器 32px；紧凑视图是表格式单行，不显示头像。列表未读态在行首占用 6px 蓝点槽位（点 + 8px 间隙），蓝点与下方主题、摘要左对齐，发件人名字随之后移 14px；已读行不占槽位，发件人直接与主题、摘要左对齐。选中行头像颜色不变、蓝点转白，主文字转纯白。
8. **滚动条是浮层，不占内容宽度**：容器加 `scrollbar-overlay` 隐藏原生滚动条（原生条会让列表、阅读器、Dialog 的内容区凭空窄 8px，并逼着列头去补让位），由 `OverlayScrollbar` 画一条 6px 宽、距右缘 3px 的固定细条浮在内容之上；**纵向条**滚动或鼠标进入时出现、停止 700ms 后淡出；**横向条**只要容器有横向溢出就常驻可见（2026-11-25 用户要求，配合「原版式」正文超宽可横滚，不靠悬停猜哪里能滚）；两条都可拖动；无轨道背景、无箭头、无两端按钮。列表、侧栏文件夹、设置、账户、搜索面板、发件人抽屉、收件人列表统一走这一套；**阅读器正文例外，用原生滚动条**（2026-11-25 用户要求）：容器加 `.scrollbar-native`，6px、透明轨道、圆角 thumb，外观照列表的浮层细条，但占位与行为保持原生；**纵向 thumb 静止时隐藏、滚动后 700ms 内或悬停时出现，横向条常显**。
9. **画布区（列表 + 阅读器）是一张悬浮卡片**（2026-11-24 用户要求）：`App.tsx` 用 `mt-2 mb-0 ml-2 mr-2 flex min-w-0 flex-1 overflow-hidden rounded-t-lg bg-card` 包住列表 → 分隔线 → 阅读器：左/上/右留 8px 露出 `--background`，**底部不圆角、直接延到窗口底**；**不画边框、不加阴影**（QQ 邮箱实测是背景色直接切白底），靠明度差形成悬浮感。卡片是唯一的边框/圆角来源：列表 `section` 只保留 `bg-card`，**不要**再给它加 `rounded-*` / `overflow-hidden` / 边框（会叠成双份）。
10. **空状态**：居中，图标 48px + `--muted-foreground`，一句文案 + 一个主按钮，不使用大插画。**演示数据只在 dev 构建存在**（`lib/mock.ts` 由 `import.meta.env.DEV` 门控，正式包的 fixtures 会被摇掉）：正式包一个账户都没有时，列表空状态固定显示「还没有配置账户 / 点标题栏左侧的账户胶囊添加 IMAP 邮箱」，侧栏不显示「标签」分组，底部同步文案显示「尚未连接账户」——不出现任何演示邮件或假同步状态。
10.5 **关闭窗口的行为可配置**：默认点窗口 × 直接退出；开启「关闭窗口时最小化到托盘」后，`close` 事件只 `hide()` 窗口（不退出、不销毁），托盘图标与未读角标继续工作，点托盘图标或菜单「打开 MailDesk」恢复窗口，只有托盘菜单的「退出」（或 `app.quit()`）才真正退出——主进程用 `before-quit` 置 `quitting` 标志放行 close，避免退出时被拦成隐藏。
10.7 **下载管理**：标题栏窗口三键左侧有「下载」按钮，点击弹出 320px 浮层（`ui/popover` 的 Radix Popover，**用组件默认样式**：`rounded-md`、`p-4`、`shadow-md`，与标题栏间距 12px），列出本次运行内的附件下载（进行中排前、最近完成最多 20 条）。进行中的显示进度条与百分比、可点 × 取消（主进程销毁 IMAP 下载流）；**已完成且已落盘的显示「打开文件夹」按钮**（`shell.showItemInFolder` 定位到文件）；失败/已取消显示状态。图标右上角有小圆点表示有进行中的下载；点浮层外或 Esc 收起。
11. **标题栏自绘且承载功能**：窗口 `frame: false`，无系统标题栏与系统按钮。标题栏高 44px（2026-11-24 用户要求加高），横向两段同色延续——左段宽度等于侧栏（220 / 折叠 50）用 L0 并放账户胶囊（图标中心与侧栏文件夹图标同一条竖线：展开 25.5px、折叠 25px），右段用 L1 并依次放「侧栏折叠开关 + 搜索 + 密度 + 拖拽留白 + 窗口三键」——搜索与密度紧贴折叠开关靠左，深浅切换留在右端、紧邻窗口三键，中间整段留给拖动窗口，形成「每个平面一直顶到窗口上沿」的连续感，不做横向色带、不加下边框。标题栏**不重复显示列表标题与未读数**（列表自己的标题行与页签已给出），也**不把列表/阅读器的分隔线延伸进标题栏**。设置入口不在标题栏，只在侧栏底部。
    - 因为这条 44px 已被功能占满，**列表不再有独立的标题行与搜索行**（原 52px 标题行 + 40px 搜索行一并上移），列表从筛选条开始，纵向多出约 90px 给邮件。
    - 右侧三个按钮各 46×44px，图标 10px 1px 描边；悬停用 `--row-hover`，关闭键悬停填充 `#C42B1C` + 白图标。窗口缩放边框、Aero Snap、双击最大化仍走 Windows 原生行为。

**落地要求**：
1. 使用 `npx shadcn@latest init` 并选择 **Vite** 模板（非 Next.js）。
2. `components.json` 配置：`"rsc": false`、`"tsx": true`、别名 `@/components`、`@/lib/utils`。

5. **只有浅色主题**，不引入 `next-themes`，也没有主题切换逻辑；`html` 的 `color-scheme` 固定 `light`。
6. 允许直接用 shadcn 的 **dashboard block**（如 sidebar 系列）作为起点，但需清理演示内容。

### 7.2 关键取舍与 shadcn 适配注意

1. **不用 Next.js**：shadcn 文档默认给 Next 示例，必须按 Vite 路径安装；组件本身与框架无关，但 `"use client"` 指令可删。
2. **Tailwind v4 的 `@theme inline`** 决定 token 写法；只保留一套 `:root` 浅色 token，不维护 `.dark`。
3. **Electron 的 `file://` 限制**：`base: './'`、HashRouter、避免绝对路径资源。
4. **Radix Portal 与多窗口**：Electron 单窗口下正常；若引入独立阅读器窗口需重新挂载 Portal 容器。
5. **字体**：不用 `next/font`，直接使用系统字体栈或 `@fontsource` 本地包（离线可用）。
6. **数据库不引原生模块**：Electron 45 自带 Node 24，`node:sqlite` 提供同步 API 且内置 FTS5，直接 `import { DatabaseSync } from "node:sqlite"` 即可，省掉 `electron-rebuild`、`asarUnpack` 与 Windows 编译链。代价是绑死 Electron 自带的 SQLite 版本；若将来需要更新的 SQLite 特性，再换回 better-sqlite3（届时按 ABI 重新构建）。

### 7.4 数据模型（SQLite）

    -- 账户（凭据单独用 safeStorage 加密存储，不进此表）
    CREATE TABLE account (
      id TEXT PRIMARY KEY,
      email TEXT NOT NULL,
      display_name TEXT,
      imap_host TEXT NOT NULL,
      imap_port INTEGER NOT NULL DEFAULT 993,
      security TEXT NOT NULL DEFAULT 'tls',      -- tls | starttls | none
      username TEXT NOT NULL,
      accent TEXT,
      created_at INTEGER NOT NULL
    );

    CREATE TABLE folder (
      id TEXT PRIMARY KEY,
      account_id TEXT NOT NULL REFERENCES account(id) ON DELETE CASCADE,
      path TEXT NOT NULL,                        -- IMAP 原始路径

      delimiter TEXT,

      uid_validity INTEGER,
      uid_next INTEGER,
      last_synced_uid INTEGER DEFAULT 0,
      total_count INTEGER DEFAULT 0,
      unread_count INTEGER DEFAULT 0,
      sort_order INTEGER DEFAULT 0,
      UNIQUE(account_id, path)
    );

    CREATE TABLE message (
      id TEXT PRIMARY KEY,
      folder_id TEXT NOT NULL REFERENCES folder(id) ON DELETE CASCADE,
      uid INTEGER NOT NULL,
      message_id TEXT,
      subject TEXT,
      from_name TEXT,
      from_addr TEXT,
      to_json TEXT,                              -- [{name,address}]
      cc_json TEXT,
      sent_at INTEGER,
      size INTEGER,
      flags_json TEXT,
      is_read INTEGER DEFAULT 0,
      is_flagged INTEGER DEFAULT 0,
      has_html INTEGER DEFAULT 0,
      has_attachments INTEGER DEFAULT 0,
      snippet TEXT,
      body_text TEXT,                            -- 供搜索/纯文本渲染，超阈值置空
      raw_path TEXT,                             -- .eml 落盘路径
      UNIQUE(folder_id, uid)
    );
    CREATE INDEX idx_message_list ON message(folder_id, sent_at DESC);

    CREATE VIRTUAL TABLE message_fts USING fts5(
      subject, from_name, from_addr, body_text,
      content='message', content_rowid='rowid', tokenize='unicode61'
    );

    CREATE TABLE attachment (
      id TEXT PRIMARY KEY,
      message_id TEXT NOT NULL REFERENCES message(id) ON DELETE CASCADE,
      filename TEXT, mime TEXT, size INTEGER, content_id TEXT, local_path TEXT
    );

    -- 凭据：密码用 safeStorage（Windows DPAPI）加密后存 BLOB，明文永不落库
    CREATE TABLE credential (
      account_id TEXT PRIMARY KEY REFERENCES account(id) ON DELETE CASCADE,
      scheme TEXT NOT NULL,                     -- dpapi | plain（加密不可用时的降级，便于识别需重登账户）
      secret BLOB NOT NULL,
      updated_at INTEGER NOT NULL
    );

    -- 设置：key/value，替代 electron-store
    CREATE TABLE setting (
      key TEXT PRIMARY KEY,
      value TEXT NOT NULL                       -- JSON
    );

迁移策略：`PRAGMA user_version` 当作迁移下标，`src/main/db/schema.ts` 里的 `MIGRATIONS` 数组按序执行未应用的条目；每次改 schema 只追加，不改历史项。

存储约定：正文（`body_text` / `body_html`）随同步一起写进 SQLite，点开不再联网；附件二进制**不进库**，只存元数据（文件名、mime、尺寸、part 号），保存/预览时按 part 下载。数据库启用 WAL 模式。

### 7.6 同步状态机

    disconnected → connecting → selecting(folder) → fetching(uid range)
        → idling ⇄ (EXISTS → fetching → idling)
        ↑                                        │
        └──── backoff(1s,2s,4s,…,60s) ←── error ─┘

规则：
- 每个账户一个 `SyncEngine` 实例，内部串行队列。
- 首次同步：`UID FETCH 1:* (FLAGS INTERNALDATE RFC822.SIZE BODYSTRUCTURE)`；正文在同一次同步里按 BODYSTRUCTURE 的 part 号取回（`BODY.PEEK[part]`），附件仍按需下载。
- **正文预下载**：列表与正文都在本地库里，点开任何一封都不再发 IMAP 请求；缺失正文的老数据由 `bodyBackfillLoop` 启动后补齐，`fetchBody` 只剩兜底作用。
- 收到 `EXISTS` 后按 `last_synced_uid+1:*` 增量，不重复解析已有 UID。
- 所有失败归一化为 `ErrCode`（network/tls/auth/unsupported/db/internal），UI 只展示错误码与一句话说明；失败同时写 electron-log（`src/main/log.ts`，M4 已接）。
- 连接用 imapflow 的 `IDLE`；持久化 `uid_validity`，变化即整箱重拉；`uid_next` 只增不减，断线重连按 `last_synced_uid+1:*` 续传。
- 正文块必须按 `Content-Transfer-Encoding`（base64 / quoted-printable）还原后再按 charset（`iconv-lite` 兜底 GBK/GB2312）解码；摘要由解码后的纯文本生成，否则中文摘要会变成乱码。

## 8. 非功能需求

### 8.1 性能

- 列表虚拟化；整箱一次载入（本地库已是全量），任何操作不阻塞 UI 线程。
- 主进程解析邮件使用流式解析，单封 > 10 MB 时限制并发为 1。
- 数据库操作全部走事务批量写入（每批 50 封）。
- 启动时只加载窗口位置与账户列表，不阻塞等待网络。

### 8.2 安全与隐私

- 密码/token 仅存于 `safeStorage` 加密后的文件，日志中脱敏。
- 邮件 HTML 一律视为不可信输入；外部图片、远程字体、跟踪像素默认阻断。
- 不接入任何统计、崩溃上报、遥测。
- `shell.openExternal` 仅允许 `http/https`，禁止 `file://` 与其他协议。

### 8.3 体积与分发

- 安装包目标 < 120 MB（Electron 基线约 80–100 MB）。
- 仅提供 Windows x64 免安装 zip + NSIS 安装包，不做代码签名（自用，接受 SmartScreen 提示）。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原生模块编译失败 | 阻塞 M2 | 已规避：改用 Electron 内置 `node:sqlite`，无原生编译 |
| 国内邮箱（163/QQ）IMAP 限制 | 收不到信 | 内置 IMAP ID、授权码引导、常见错误码映射；QQ 需在网页端开启 IMAP |
| 中文/GBK 邮件乱码 | 阅读体验崩坏 | iconv-lite 按 charset 声明 + 启发式兜底（GB18030 万能解码） |
| HTML 邮件破坏布局 | 视觉不可控 | webview 隔离 + 注入归一化 CSS + 默认拦截外链资源 |
| 大邮箱首次同步慢 | 首启体验差，正文全量下载更占带宽 | 首屏只等 200 封；历史与正文由后台 `backfillLoop` / `bodyBackfillLoop` 分批补，不阻塞交互 |
| shadcn 组件风格过于"Web 形" | 不像桌面邮件应用 | 通过 token 与密度定制；重点重写列表行、阅读器头部 |
| Electron 内存偏高 | 常驻体验差 | 单窗口、限制缓存、关闭 DevTools、必要时 `backgroundThrottling` 调整 |
