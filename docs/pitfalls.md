## 已知坑

- `MAILDESK_CAPTURE` 走 bash 时，MSYS 会把 `/d/...` 转成 `D:\d\...`：值用 Windows 反斜杠路径并加 `MSYS_NO_PATHCONV=1`。
- **Vite 在 Windows 上会吞掉同一秒内的 mtime 事件**：磁盘已是新代码、dev server 也能 `curl http://localhost:5173/src/components/X.tsx` 看到新内容，但窗口不刷新。判断方法就是 curl 一次；确认是新代码后重启 dev（`job_kill` 旧 job 再 `npm run dev`），不要靠反复改文件赌 HMR。
- 主进程有单实例锁，第二个实例会直接退出——所以「dev 在跑」时截图会静默失败（`cap.log` 无 `captured`）。
- 只有浅色主题，不存在 `maildesk.theme`；截图脚本里残留的 theme 注入不会再改变外观。
- 需要看「选中邮件」的阅读器状态时，加 `MAILDESK_CAPTURE_SELECT=1`，截图前会自动点第一行；`MAILDESK_CAPTURE_ROW=n` 点第 n 行、`MAILDESK_CAPTURE_ACCOUNT=<邮箱片段>` 先切账户、`MAILDESK_CAPTURE_SCROLL=<px|1>` 滚动阅读器（1 表示滚到底）。列表视图与侧栏折叠的持久化 key 是 `localStorage["maildesk.density"]`（`compact`/`standard`；旧值 `comfortable` 读取时归到 `standard`）与 `localStorage["maildesk.sidebarCollapsed"]`。另外列表宽度是 `localStorage["maildesk.listWidth"]`（320 ~ 窗口一半，默认 380，双击分隔线复位；上限用 `listMaxWidth(window.innerWidth)` 动态算，窗口 resize 时要夹一次）；分隔线本身就是拖拽把手（5px 命中区，`-mx-[2.5px]` 跨在边界上），所以 Reader 不能再自带 `border-l`，否则叠成 2px。
- Radix 的触发器只认真实指针事件：截图脚本里 `.click()` 打不开下拉菜单，必须依次 dispatch `pointerdown/mousedown/pointerup/mouseup/click`。
- **邮件自造的小滚动框要放开**（用户 2026-11-24 要求）：`unclipScrollBoxes()` 在 `prepare()` 里把「内联 `height`/`max-height` + overflow auto/scroll/hidden」的定高改掉（< 24px 跳过，那是 preheader 隐藏块），`handleLoad` 里的 `releaseScrollBoxes()` 再按计算样式兜一次（这样才能盖过类选择器和 `!important`，用 `setProperty(..., "important")` + `data-maildesk-unclipped` 去重），加载后 120ms/600ms 与 `fonts.ready` 时各再跑一次。别把它做成无条件删高度：0 高度的隐藏块被放开会把 preheader 文案顶出来。
- **统一容器 / 宽度重排已删除（2026-11-25 用户要求，不要再加回）**：正文固定「原版式」，不再拆邮件自带的页面容器、不改页面级定宽、不按比例缩放表格。`unifyContainer` / `fluidWidths` / `scaleTableColumns` / `data-maildesk-table` / `releaseNowrap` 都已从 `HtmlBody` 移除；也不要恢复 `setting.bodyFit`、`fitMode`、`adapt` 分支或「正文适配方式」设置项。
- **正文只有原版式一种**：`prepare(raw, allowRemote)` 只做清洗、放出邮件自造的小滚动框、把远程/内嵌图片换成占位；`baseCss(fontSize)` 只设字体、颜色与引用样式，不覆盖页面底色、不压宽、不缩放。`measure()` 先按阅读区宽度排一遍量 `scrollWidth`，再用「元素写死的最大宽度（≥240px）」推定设计宽度，取 `width = max(pane, design, laidOut)` 写回 iframe（**只铺宽不缩、不裁剪**），高度按该宽度实测。没有 `transform: scale`，右键坐标 1:1 直接加 `getBoundingClientRect()`。**宽度只在「阅读区宽度变了 / 显式 force」时重算**（初始、`fonts.ready`、120/600ms、图片 load、窗口 resize、松手补量）；`ResizeObserver` 的回调只能更新高度——它只观察 `frame` 与正文容器，而两段式测量（先缩回 pane 再按内容撑开）本身就会改 iframe 宽度，若每次 RO 回调都重算，宽度会在 pane↔content 之间每帧来回跳，Chrome 就刷 `ResizeObserver loop completed with undelivered notifications`（2026-11-26 实测 dev 日志 10 分钟 9.9 万条）。回调里必须写 `new ResizeObserver(() => measure())`，**不能**写 `new ResizeObserver(measure)`——RO 会把 entries 当第一个参数传进去，等于每次强制重算宽度。**也不要用主窗口的 `ResizeObserver` 去 `observe()` 邮件 iframe 文档里的节点**（`doc.body` / `doc.documentElement`）：Chromium 会把跨文档的尺寸变化记成「无法投递的通知」，回调不派发给我们、却每帧报一条 `ResizeObserver loop completed with undelivered notifications`（2026-11-26 实测 250 条/秒、同时我们包住的 observer 回调数为 0）。内容变化改由 `MutationObserver`（没有布局循环语义）+ 图片 `load` + `fonts.ready` + 120/600ms 补量；主文档的 RO 只观察 `frame` 与正文容器。
- **滚动条只有阅读区一个**（用户 2026-11-24 要求「滚动条交给 app，不要邮件里再套一层」）：iframe 必须带 `scrolling="no"`，正文文档 `html, body { overflow: hidden !important }`，高度靠实测内容高度写回 `style.height`（主文档的 `ResizeObserver` 盯 `frame` 与正文容器 + 邮件文档的 `MutationObserver` + 图片 `load` + `fonts.ready` + 120/600ms 补测；不要跨文档 observe 邮件文档节点，见上一条）。原版式不压宽、不缩放：iframe 按邮件设计宽度铺开，**超宽内容由阅读区自己的原生横向滚动条接手（兜底是横滚，不是裁剪，也不是缩放）**；`Reader` 的正文容器是 `overflow-auto`（2026-11-25 用户要求：正文滚动条改回原生，纵向与横向都由这个容器画）。正文容器在**列表模式**下是 `max-w-[900px]`（横向边距只由 `article` 的 `px-6`（24px）控制，这个宽度只决定正文起始位置、不再用来压邮件版式）；**双击进入邮件页签后放开这条上限**（`Reader` 的 `wideBody`，2026-11-27 用户要求：页签模式正文独占整块画布，900px 会让“双击给更多空间”名不副实；`pane` 随之变成画布宽 − 48，定宽内容照样按内容宽度铺开，纯文本另有 `max-w-[76ch]` 兜住行宽）。**阅读器里正文外面只有一个直角矩形容器、不画边框**（HTML 与纯文本两个分支各自的容器是 `w-full flex-1 pt-4 pb-5` + 列表模式加 `max-w-[900px]`；2026-11-24 用户要求去掉那圈 1px 直角框，正文直接落在白画布上，`bg-card` 可省略；**不要圆角、不要 `mx-auto`**——用户要求窗口拉伸时内容不往中心挪；**页头与正文之间有一道 1px `border-table-line` 分隔线**（`mt-4` 起、正文容器 `pt-4 pb-5`，正文不存在时不画），不要把它包进页头或正文容器里；`article` 必须是 `flex min-h-full flex-col`，`flex-1` 才能把卡片高度撑到阅读区底部），只标出正文容器范围；主题、发件人、收件人、附件 chip 都在卡片外（用户 2026-11-24 定稿）。它是阅读区唯一的正文容器，别再往正文里加卡片或边框、也不要把 header 包进去。
- **`prepare()` 必须用 `DOMPurify.sanitize(raw, { WHOLE_DOCUMENT: true })`**：默认模式只返回 body 内容，`<head>` 里的 `<style>` 会被整块丢掉（2026-11-24 实测 457 封里 189 封中招），字体族 / 字号 / 行高 / 媒体查询 / `body` 背景全部失效；要把 `doc.head` 里的 `<style>`（保留 `media`）搬进最终文档的 `head`，并把 `<html>`/`<body>` 的 `style`/`bgcolor`/`background`/`class`/`dir`/`lang` 合并回去。原版式不再强制 `background: transparent`，邮件自带的页面底色保留。**但 `html`/`body` 的高度声明必须剥掉**：营销邮件常写 `<html style="height:100% !important">` / `body { height:100% !important }`，内联 + `!important` 盖过基线样式，body 被钉成 iframe 视口高度，`body.getBoundingClientRect().height` 与 `documentElement.scrollHeight` 都只剩一屏，正文被 `overflow:hidden` 裁在首屏——实测 Microsoft Rewards 那封只显示了顶部横幅（2026-11-27）。现在 `attrsOf()` 用 `stripSizeDecls()` 去掉 `height`/`min-height`/`max-height` 三条内联声明，并在**邮件样式之后**再追加一段 `html, body { height:auto !important; min-height:0 !important; max-height:none !important }` 守卫。`prepared` 已经是对象，`document_` 的 `useMemo` 依赖整个 `prepared`，别改回只依赖 `prepared.html`。
- **HTML 正文不要抹平邮件自带的浅色底板**：抹掉 `bgcolor` / `background` 后深色字可能落在画布上对比不足（招商银行账单那次翻车）。现在保留 `bgcolor`/`background`/`<style>`，再靠 HtmlBody 的对比度归一化兜底「没写底色的深字」。别给 `td/th` 加 padding、别加全局 `* { max-width: 100% !important }`，会把定宽单元格压窄导致数字折行；图片只限制 `max-width`，不限制高度比例的写法不要改。
- **HTML 正文的用户可达面都在 iframe 里收口**（`HtmlBody.tsx`）：
  - 远程图片默认放行；拦截态给 srcDoc 注入 CSP，把 `@import`、`background-image: url()`、`@font-face` 这些「不用 `<img>` 也能联网」的通道一起堵死，只放开 `img-src data:`。只替换 `<img>` 是不够的，PRD 的「拦截时零外部请求」靠 CSP 成立。
  - 链接用 `click` 委托：`#` 锚点放行给 iframe，`http(s)`/`//`/`mailto:`/`tel:` 走 `mail.openExternal`（主进程白名单已含 mailto/tel），其余 `preventDefault`；不要恢复成「每个 `<a>` 挂 preventDefault 且只认 http(s)」，那会让 mailto 和页内跳转点了没反应。
  - 长引用（`blockquote` / `.gmail_quote` / `#divRplyFwdMsg` / `.yahoo_quoted`）超过 260px 或 500 字就折叠成「显示引用内容（N 字）」横条；折叠/展开靠 body 的 ResizeObserver 自动重算 iframe 高度。
  - **`cid:` 内嵌截图在同步时就会取回**：`collectInlineImages` 找出带 Content-ID 的 image part，`fetchBodies` 把它们的二进制按 base64 转 data URL 嵌入 HTML（单张 ≤10MB 编码尺寸、整封 ≤16MB 解码合计），渲染时直接可见；超过上限或取不到的仍回退透明占位 + `alt="内嵌图片"`。旧正文里的 cid 占位由 schema v9 清空一次，交给 `bodyBackfillLoop` 重新预下载。**上限曾经是 2MB/8MB，正好卡死整封 2MB 以上的纯图片宣传邮件**（2026-11-26 用户在公司实测）：`image.size` 是 base64 后的尺寸，比原图大 1/3，所以「整封 2MB」的邮件里那张图就已经超限、被整张跳过，纯图正文于是渲染成一片空白；别再按 2MB 收。跳过时 `fetchBodies` 会打 `[sync] inline image skipped`（logger 会落 `main.log`），先看日志再改上限。
  - 失效图片必须在 iframe 里接 `error`：声明尺寸 ≤2px 的追踪像素直接 `remove()`，其余**把 `<img>` 整体替换成同尺寸的浅灰占位 `<div>`**——只删 `src` 会留下空 `<img>`，Chrome 仍然画碎图图标（实测）。否则 Chrome 会画碎图图标（招行「每日信用管家」末尾那个 1 字节 jpeg 就是追踪像素），而用户对比 QQ 邮箱时会觉得“原邮件没有这个破图”。
  - **iframe 不再做整页 `zoom` 自适配**：旧实现按内容宽度把整封邮件缩到 0.6，公司邮件的固定 slogan 图会让每封信都像一张缩小截图（用户 2026-11-23 实测否掉）。现在只量内容高度；超宽表格由 iframe 自身横向滚动，不要再加 zoom 或 `transform: scale()` 去「适配」。

- **关闭到托盘**：设置项 `closeToTray`（默认 false）。`win.on("close")` 里读 `getSettings().closeToTray`，为真就 `event.preventDefault()` + `win.hide()`；`app.on("before-quit")` 先把 `quitting = true` 放行 close，否则托盘菜单的「退出」会被拦成隐藏。判断必须在 close 时读库（设置是渲染层写 SQLite 的），不要缓存到渲染层再 IPC。

- **只删文件夹时也要发 `reconcile` 事件**：`reconcileAccount` 原本只在 `added/moved/removed/flags` 有一个大于 0 时才 `hooks.emit`。删文件夹这几个计数全是 0，于是渲染层不重拉 `folders:list`，启动瞬间取到的旧清单（还带着已删文件夹）会一直留在侧栏——用户看到的「我在服务器删了为什么还在」就是这个。现在 `refreshFolders()` 返回删除数量，并计入发事件的判断。
- **QQ 的 MOVE 不支持 UIDPLUS**：`messageMove` 返回的 `copy.uidMap` 是空对象，目标 uid 只能靠对账重新枚举；且草稿（非系统 `Drafts`）里放进去的邮件约 2 分钟后会被 QQ 自己清空，测移动别用「草稿」。
- **QQ 有"幽灵 UID"**：`EXISTS`/UID 列表里会多出一封 `fetchOne` 永远拿不到 header、也没有 `Message-ID` 的空 UID（2026-11 时为 2533），所以「服务端封数 = 本地行数」会差 1，不是本地漏同步。增量拉取取不到某封时 `last_synced_uid` 仍会推进，靠下一轮对账补回。确实要清掉时用 `MAILDESK_IMAP_OP='deleteuid|2533'`（按 UID 直接 STORE \Deleted + EXPUNGE，`runServerOp` 会打印 `existsBefore` 与操作后的 `exists` 供核对）——按主题匹配永远找不到这种 UID。
- 本地移动/删除走 `mail.messages.move/remove`：`remove(ids, permanent)` 的第二个参数在垃圾箱里为 `true`（EXPUNGE）。Reader 工具栏的删除按钮 title 由 `permanentDelete` 决定，别写死「删除」。
- **QQ 的多 UID EXPUNGE 会漏删**：`messageDelete("uid1,uid2,uid3", { uid: true })` 不报错，但实测只消失一封，其余留在服务器；本地行却已删，下一轮对账又拉回来 → 用户报「全选后只删一条」。`purgeByFolder` 现在删完会 `fetch` 复查剩余 UID、逐封补删，只对确认消失的行删本地，剩下的计入 `failed`。改删除逻辑时别把复查省掉。
- 批量菜单操作（右键「移动到…」「复原」「删除」）要先看这行是否在 `selectedIds` 里，在就整批带走（`moveMessage/deleteMessage` 里的 `ids` 展开），否则 `Ctrl+A` 后从菜单删只掉一封。**「移动到…」的候选列表在默认（系统）文件夹与自建文件夹之间有一条分隔线**（2026-11-27 用户要求）：`App` 的 `moveTargets` 用 `liveFolders` 里 `role === null` 的 id 集合找第一个自建项，标上 `dividerBefore`，阅读器工具栏下拉与右键子菜单各渲染一个 `DropdownMenuSeparator` / `ContextMenuSeparator`；候选被过滤（当前文件夹、不可选容器）后要重新算边界，不能沿用侧栏 `navFolders` 上挂的那个标记。**这两个菜单的高度要跟随内容、不要内滚动**（2026-11-27 用户要求）：shadcn 的 `DropdownMenuContent` / `ContextMenuSubContent` 基类带 `max-h-(--radix-*-available-height) + overflow-y-auto`，候选一多就被截成带滚动条的一条，所以在这两处用 inline `style={{ maxHeight: "none", overflowY: "visible" }}` 覆盖（inline 才压得住那个 CSS 变量），不要改全局基类。
- 调试服务器侧操作：`MAILDESK_IMAP_OP='delete|主题' / 'move|主题|目标文件夹' / 'folders' / 'peek|文件夹路径' / 'moveall|源|目标' / 'append|邮箱' / 'raw|UID'`（`append` 走 IMAP APPEND 把一封 30 收件人 + 30 抄送的样例邮件放进自己的邮箱，不经过 SMTP；`raw` 打印 To/Cc 原始头，排查编码与姓名） 会走 `runServerOp` 并打印 `SERVEROP {...}`（`peek` 列出某箱 UID+主题，`moveall` 分批 50 把整箱搬走）；`messageMove` 结果含 BigInt，直接 JSON.stringify 会抛错（用 selftest 里的 `safe()`）。
- 对账/回溯的日志只在 `MAILDESK_SYNC_DEBUG=1` 时输出（`[sync] scan`、`[sync] folder`）；日常 dev 不要带这个 env。
- **图片预览浮层的关闭状态**：浮层由 `preview || previewBusy || previewError` 三个状态驱动，关闭必须走 `Reader.tsx` 的 `closePreview()` 一起清三个 state。只 `setPreview(null)` 时失败态（`previewError` 有值、`preview` 为 null）会永远留在屏幕上，用户会以为整个窗口卡死。判断「能不能预览」只用 `attachment.mime` 的 `image/` 前缀或图片扩展名（`isPreviewable`），不要用 `Attachment.type`——那是图标分类，压缩包会被送进预览接口然后报 `unsupported`。
- **附件尺寸一律取自 BODYSTRUCTURE**：正文预下载只取正文 part，附件二进制不同步传输；`fetchBody` 现在走同一条「结构 + part」路径，尺寸同样取 part octets（旧实现取整封前 512KB，解析器对截断附件给出的 `item.size` 只是残片，实测 40 MB 的附件报 369 KB）。两条路径都用 `collectAttachmentParts()` 的 part octets 覆盖尺寸，base64 按 76 字符 + CRLF 折行折算：`(size − ceil(size/78)×2) × 3/4`（直接乘 0.75 会偏大 3%，40 MB 显示成 41.1 MB）。
- 列表「大小」列是整封信的 RFC822 字节（`envelope.size`，含 base64 膨胀），附件 chip 是解码后的文件大小——两者本来就不相等，别当成 bug 去「对齐」。
- 移动/删除是「服务器先行」，断线时本地不变——渲染层**不能 `.catch(() => undefined)` 静默吞错**，否则用户看到「点了没反应」。统一走 `App.tsx` 的 `showNotice()` + `src/renderer/src/components/Notice.tsx`（底部居中，3.5 s 自动消失），错误串统一用 `src/renderer/src/lib/ipc.ts` 的 `describeIpcError()`（按 `code` 精确匹配，别再用 `includes("network")` 那种子串判断；原始说明用同文件的 `ipcErrorMessage()`，两者共用 `parseIpcError()`）。主进程侧一律 `throw ipcError("network", "…")`（`src/shared/errors.ts`，错误码只在那里维护），不要手拼 `code: message`。
- **邮件行右键菜单**用 Radix `ContextMenu`（聚合包 `radix-ui`，shadcn 风格的 `src/renderer/src/components/ui/context-menu.tsx` 已补齐）：`MessageList` 在虚拟行外层包 `<ContextMenu onOpenChange={open => open && onContextSelect?.(item.message.id)}>` + `<ContextMenuTrigger asChild>`，**分组行（GroupHeader）不要包**。右键只调 `setSelectedId`（高亮 + 切阅读器），**绝不能调 `select()`**——那会顺手标已读，右键扫一眼就丢未读。菜单项复用 `markRead/toggleStar/moveMessage/deleteMessage`，别在菜单里另写一套；「标为垃圾邮件」= 移动到 `role === "junk"` 的文件夹，当前已在垃圾箱/垃圾邮件时 `junkFolderId` 传 `undefined` 隐藏该项。垃圾箱里额外有「复原」（onRestore，走 moveMessage 回收件箱，role === "inbox"）：非垃圾箱时 App 传 undefined，组件再按 permanentDelete 兜一层隐藏；本项目不记录原始文件夹，复原一律回收件箱，别在 UI 上暗示能回到原子文件夹。没有标签系统，菜单里没有「标签」，不能造一个假的。
- **多选与 Ctrl+A**：选中集合是 `App.tsx` 的 `selectedIds: string[]`，`selectedId` 只是其中的「活动行」（决定阅读器与滚动定位）。`Ctrl/⌘+点击` 由 `MessageRow` 传 `event.ctrlKey || event.metaKey` 给 `onSelect(id, additive)`，**只增减集合、不标已读**；`Ctrl+A` 无条件全选整个当前文件夹（用 `folderMessages` 而不是 `visible`，并 `setFilter("all")` 让被过滤掉的行也显示出来变成蓝底），同样不标已读，并且不触发「停留 1.5s 自动已读」那个 effect（有多选时直接 return）。`useHotkeys` 里对输入框内的 `ctrl+a` 单独放行，否则搜索框/账户表单里按 Ctrl+A 会被列表全选吃掉。`Delete`/`Backspace` 走 `deleteSelected()` 批量删（垃圾箱内 `permanent`），`J/K` 移动会收敛回单行。`Shift+点击` 是范围选择（`select(id, additive, range)`，anchor 取 `selectedId`，在当前 `visible` 里切片），不标已读；`Shift+U` 走 `markAllRead()` 一次 `setRead(ids, true)` 批量标记，同时乐观更新 `items` 与 `searchResults`（搜索态跨文件夹时不直接改 `unreadCounts`，靠 `unreadTick` 回读）。**行底色必须由 `selectedIds` 决定**（`MessageList` 里 `selectedSet = useMemo(() => new Set(selectedIds ?? []))`，只有集合为空时才回落到 `selectedId`）——只比 `selectedId` 会让 `Ctrl+A` 看起来「没反应」，其实集合已全选、只是只亮了一行（实测 `aria-selected` 从 0 到 36）。
- **居中弹窗必须整数像素**：`src/renderer/src/components/ui/dialog.tsx` 的 `DialogContent` 用 `offsetWidth/Height` 与 `window.innerWidth/Height` 算整数 `left/top`，并把 `translate` 设为 `none`；不要改回 `top: 50% + translate(-50%)`。半像素位置会把 1px 标题线抗锯齿成两行（账户 vs 设置），窗口缩放或内容改高时用 rAF 重算。
- **hover 与选中不能连成一块**：圆角块状的可点列表（设置左侧分区、侧栏文件夹、任何 `rounded-md` 导航项）容器必须带 `gap`（`gap-px` 起，`gap-0.5` 更稳），不能 0 间隙紧贴——选中的蓝块和相邻行的 hover 灰块会拼成一个大色块，看起来像同时选中两项（2026-11-28 用户第二次指出）。表格行是整行铺满、无圆角、靠 `--row-line` 分隔，不属于这一类。
